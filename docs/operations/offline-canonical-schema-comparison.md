# Offline canonical schema comparison — review-only

This tool compares **two previously exported** JSON files produced by `database/scripts/schema-manifest.sql`. It does not connect to Neon, run SQL, accept credentials, create ledger rows, change schema, or claim source-database parity by itself.

```bash
node database/offline/compare-schema-manifests.mjs source-manifest.json target-manifest.json
node --test database/offline/compare-schema-manifests.test.mjs
```

Exit codes: 0 = exact manifest parity, 1 = drift, 2 = malformed input. The output prints changed **object identities only**, not function bodies, policy expressions, ACL values, user data or secrets. Manifest files should remain in protected artifacts; do **not** commit real organizational role inventories to the repository.

The comparison deliberately detects differences in database metadata and server version; reconcile environmental differences with explicit reviewed evidence rather than silently suppressing them. A result of PASS is limited to fields included in the manifest v1 contract. `pg_dump --schema-only`, source-owned migration checksums, effective ACL grants, backup/restore, PITR/RPO/RTO, production authorization and data parity are separate gates.

**Read-only baseline evidence (2026-11-12):** legacy source and NEW Development share 182 columns, 244 constraints, 41 policies, 63 indexes, 12 triggers and 24 enum labels with identical catalog fingerprints. Their routine set differs on `iam.set_tenant_context`'s SECURITY DEFINER `search_path` and `app_private.context_keys` has an explicit owner relacl on legacy but NULL relacl on NEW Development. The legacy ledger has 1 historical entry, while NEW Development has 0; NEW Production has no IAM schema. These are findings, **not** approval to fabricate a ledger or execute migration.

## Legacy migration ledger reconciliation (read-only)

`database/offline/compare-migration-ledgers.mjs` validates two **sanitized** `iam-ledger-provenance/v1` JSON documents. Each document needs `branch_id` and `rows` from `iam.schema_migrations`; each row carries `migration_id`, `checksum_sha256`, `source_sha`, `execution_role` and `applied_at`. Store originals in protected temporary storage, never commit a live connection string or any identity.

```bash
node database/offline/compare-migration-ledgers.mjs source-ledger.json destination-ledger.json
node --test database/offline/compare-migration-ledgers.test.mjs
```

Exit 0 means **METADATA_MATCH_ONLY**, not that a migration is safe to replay. Exit 1 means **BLOCKED** (missing/unexpected ID, mismatch of immutable checksum, source commit or execution role). Exit 2 means malformed input. The tool never writes to either database, copies ledger rows, or derives an execution plan. A destination ledger with zero rows against an origin with one verified migration is **BLOCKED**, even if schema manifests otherwise match. Full DDL, migration file bytes, database history, owner privileges, PITR/restore and approved cutover remain separate gates.

## SHA-256 of routine bodies — mandatory for manifest v1 generated by PR #44

The exporter now records `definition_sha256` (the SHA-256 of `pg_get_functiondef`, not the function source) for each function/procedure/window routine. Aggregates are recorded by their separate aggregate contract; any function/procedure with a missing, malformed or forged-length SHA is rejected as **invalid input** (exit 2), even when function name, owner and `search_path` match. A different body hash is **DRIFT** (exit 1) and reveals only the routine identity.

See the sanitized [live catalog drift inventory](../evidence/neon-canonical-drift-inventory-2026-11-12.md). On 2026-11-12, read-only catalog comparison across the **actual** source/Development branches found **58 full-manifest differences across seven categories** (including provider role/ownership differences), despite equal application object counts. This is **BLOCKED** for canonical migration and cutover until reviewed disposition of every material difference. Do not weaken the target's SECURITY DEFINER search_path to imitate the legacy source.

## Ordered PostgreSQL semantics — regression corrected 2026-11-12

The comparator now **preserves nested array order**. In particular, the ordered `enum_labels` array is derived from PostgreSQL `pg_enum.enumsortorder`; sorting it alphabetically would incorrectly mark two ENUMs with different comparison semantics as equal. Only the top-level collections keyed by stable object identity are order-insensitive. New regression tests cover swapped enum labels, nested column-order drift and shuffled top-level object collections.

Evidence: PostgreSQL18 and `quality` checks on PR #44 HEAD `2bbc0503cc5472073356515b9865738dac60f9b4` succeeded. This is a **comparator correctness test**, not authorization for historical ledger insertion, DDL apply or Production cutover.
